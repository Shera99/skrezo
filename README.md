# Skrezo — Platform API

Бэкенд **платформенной зоны Skrezo** (админка команды) и **входа сотрудников
клиник** для стоматологической платформы. Сервис отвечает за провижининг
клиник и соло-врачей, заявки, тарифы, подписки и биллинг Skrezo ↔ клиника,
платежи и дашборд, а также за вход сотрудников клиник (владелец/менеджер/
работник) в рабочее приложение по **телефону и паролю**.

> **Клиническое ядро — источник правды здесь.** Пациент **глобальный** (общий на
> всю платформу), история лечения **сквозная по всем клиникам**; врач = наш
> `membership`. Модули `patients`/`services`/`appointments`/`schedule`. Касса —
> следующая итерация. Вход **пациентов** по OTP — в приложении glo, здесь не
> реализуется.

## Область (scope)

| В скоупе | Вне скоупа |
|---|---|
| Платформенная зона `/admin/*` (клиенты, тарифы, подписки, платежи, дашборд, аудит) | Касса клиники (оплата приёмов) — следующая итерация |
| Клиническое ядро: глобальные пациенты, одонтограмма (FDI), услуги, приёмы, сквозная история зуба | Мобильное приложение пациента glo (вход пациентов по OTP) |
| Расписание клиники: лента дня, свободные слоты, часы работы и графики врачей (таймзона клиники) | Онлайн-запись пациентом самостоятельно (приложение glo) |
| Вход сотрудников клиник по телефону + паролю (временный пароль → смена при 1-м входе) | Вход пациентов по OTP (приложение glo, вне сервиса) |
| Провижининг: лид-форма, ручное создание (клиники заводит только команда Skrezo) | Кабинет клиники (веб-офис) — отдельная фаза; роли команды Skrezo (v2) |
| Триал 1 мес (бесплатно всем, без карты), тарифы (каталог, ступени) | Автобиллинг: карта, списания, продление, платёжный провайдер |

## Архитектура

Модульный монолит с элементами DDD. Каждый модуль — ограниченный контекст со
слоями `domain` / `application` / `infrastructure` / `api`. Подробно —
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

- **FastAPI** (async) + **Uvicorn**
- **PostgreSQL** + **SQLAlchemy 2.0 (async)** + **asyncpg** + **Alembic**
- **Redis** — кеш, rate-limit, refresh-токены (allowlist), брокер задач
- **Arq** — фоновые задачи: расписание (подписки, уборка) и очередь из API (доставка сообщений)
- **PyJWT** (единый контур токенов), **argon2** (пароли всех аккаунтов)

## Требования

- Python **3.14** (проект запинен на 3.14 через `.python-version`; образ — `python:3.14-slim`)
- [uv](https://docs.astral.sh/uv/) — менеджер зависимостей
- Docker + Docker Compose (для Postgres/Redis и полного стека)

## Запуск

### Через Docker (весь стек)

```bash
cp .env.example .env
make up            # соберёт образ, поднимет postgres+redis+api+worker, прогонит миграции
# API:     http://localhost:8010
# Swagger: http://localhost:8010/docs
# ReDoc:   http://localhost:8010/redoc
```

> **Порты намеренно нестандартные** (API `8010`, Postgres `5434`, Redis `6380`), а
> имя compose-проекта закреплено как `skrezo`. На одной машине обычно крутятся
> соседние сервисы, занимающие `8000`/`5432`/`5433`/`6379`; без этого `compose up`
> падает с `port is already allocated`, а совпадение имени проекта позволяет
> compose «усыновить» и снести чужие контейнеры по `--remove-orphans`. Порты
> публикуются только на `127.0.0.1` — наружу сервис выставляет обратный прокси.

### За обратным прокси (поддиректория домена)

Если сервис живёт не на своём домене, а под префиксом (например
`https://host/skrz/`), нужны две вещи:

1. **`ROOT_PATH=/skrz`** в окружении — иначе Swagger/ReDoc запросят
   `/openapi.json` по абсолютному пути и получат спеку соседнего сервиса с того
   же домена. С переменной ссылки станут `/skrz/openapi.json`.
2. **Прокси срезает префикс** — слэш в конце `proxy_pass`:

```nginx
location = /skrz { return 301 /skrz/; }          # без слэша иначе уйдёт в location /

location /skrz/ {
    proxy_pass http://127.0.0.1:8010/;           # слэш в конце срезает /skrz/
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto https;
}
```

> Uvicorn запускается с `--proxy-headers --forwarded-allow-ips='*'`: за прокси
> реальный IP приходит в `X-Forwarded-For`, а peer'ом выступает docker-шлюз. Без
> этого `request.client.host` одинаков у всех, и IP-лимиты (OTP-верификация,
> лид-форма) схлопываются в **один счётчик на всех пользователей**.

### Нативно (для разработки)

```bash
cp .env.example .env
make install       # uv sync
make infra         # поднять только postgres + redis в docker
make migrate       # применить миграции (создаст таблицы + сид справочников)
make run           # uvicorn с автоперезагрузкой
```

## Эндпоинты

> **Все суммы — целые тыйыны** (1/100 сома), поля несут суффикс `Tiyin`
> (`priceTiyin`, `amountTiyin`, `outstandingTiyin`). В целых сомах не выражается
> результат обычной скидки — 15% от 4250 сом = 637,5, и эти полсома некуда деть.
> Конвертации на границе API нет: клиент отправляет и получает тыйыны.

Пути даны с префиксом `/api/v1` (кроме `/health`). Админ-панель (веб-офис
команды) реализована по контрактам фронта 1:1.

**Служебное и аутентификация**

Вход **сотрудников клиник** (команда Skrezo, владелец/менеджер/работник) — телефон
+ пароль, один JWT-контур. **Соло-врачи** входят и регистрируются по **OTP**
(passwordless). Доступ разграничивают роли: `isPlatformAdmin` → админ-панель
`/admin/*`; членство в клинике + права (RBAC) → `/clinic/*`.

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/health` | Проверка живости |
| `GET` | `/cities` · `/specializations` | Справочники (публичные, для формы регистрации) |
| `GET` | `/admin/refs/cities` · `/admin/refs/specializations` | Справочники для админки |
| `POST` | `/auth/login` | Вход сотрудника клиники по телефону + паролю |
| `POST` | `/auth/otp/request` | Соло: запросить OTP-код (шаг 1); ответ не раскрывает наличие аккаунта |
| `POST` | `/auth/otp/verify` | Соло: подтвердить код (шаг 2) → вход (passwordless) или `registrationToken` |
| `POST` | `/auth/solo/register` | Соло: анкета (имя, профессия, город) → аккаунт + 30-дн. триал + вход |
| `POST` | `/auth/change-password` | Смена пароля (в т.ч. обязательная при 1-м входе) |
| `POST` | `/auth/password/forgot` | «Забыл пароль»: код на телефон (шаг 1); ответ не раскрывает наличие аккаунта |
| `POST` | `/auth/password/reset` | Новый пароль по коду (шаг 2); прежние сессии отзываются |
| `POST` | `/auth/select-clinic` · `/refresh` · `/logout` | Выбор клиники, токены, выход |
| `GET` | `/auth/me` | Профиль + активная клиника + права + `isPlatformAdmin` |
| `POST` | `/leads` | Лид-форма «Больше одного» (публичная) |
| `POST` | `/clinic-applications` | Заявка клиники после OTP: название, город, кол-во врачей (телефон — из билета) |

> **Доставка OTP.** Каналы задаются `OTP_CHANNELS` **в порядке приоритета**:
> `telegram,whatsapp,sms` — сначала бесплатный Telegram Gateway, при неудаче
> WhatsApp-бот, и только потом платная SMS (SMSPRO / nikita.kg). Переход к
> следующему каналу автоматический: у части номеров нет Telegram, и без этого
> вход для них не работал бы. Не сработал ни один — `502 otp_delivery_failed`,
> а не тихий «успех»: иначе пользователь ждёт код, которого не будет.
>
> Тексты: SMS — латиницей (кириллица переводит сообщение в UCS-2, где сегмент
> 70 символов вместо 160 — вдвое дороже), WhatsApp — по-русски, Telegram текст
> не принимает вовсе (свой шаблон). Каналы без заполненных настроек в цепочку
> не попадают и пишут об этом в лог на старте. `OTP_CHANNELS` пуст — код уходит
> в лог: так живут разработка и тесты, **в прод так выпускать нельзя**.
>
> **Уведомления (не OTP).** Данные для входа новому владельцу клиники и
> добавленному сотруднику, лид — в чат команды. Каналы задаёт `NOTIFY_CHANNELS`
> (`whatsapp,sms`) — те же провайдеры, что у кода, но с произвольным текстом,
> поэтому Telegram Gateway сюда не годится. Отправка **фоновая**: ответ не ждёт
> провайдера, а недоставка не отменяет операцию — сотрудник добавлен, клиника
> создана, лид записан. Ошибка уходит в лог (`notification_failed`). Временный
> пароль по-прежнему возвращается в ответе API — сообщение его дублирует.
>
> **Соло по OTP.** Впервые: `otp/request` → `otp/verify` (нет аккаунта →
> `registrationToken`) → `solo/register` (имя + профессия + город) → соло-аккаунт
> без пароля, клиника `solo`, 30-дневный триал, сразу вход. Повторно: `otp/request`
> → `otp/verify` → вход. Номер сотрудника клиники (с паролем) по OTP не логинится
> (`409 use_password_login`). Каналы не настроены — код уходит в лог, при
> `OTP_EXPOSE_CODE=true` (dev) возвращается в `devCode`.
>
> **Клиника с сотрудниками** — второй путь после шага 2: вместо анкеты соло
> клиент отправляет `POST /clinic-applications` (название компании, город,
> кол-во врачей `2-5|6-10|10+`; телефон берётся из того же `registrationToken`).
> Клиника **не создаётся автоматически** — заявка попадает в админку Skrezo со
> статусом `pending`, команда рассматривает её и заводит клиента вручную.

**Расписание (клиент-сайд + RBAC).** Экран «Сегодня»: колонки — врачи, строки —
часовая сетка. Часы работы и общий обед — у клиники по дням недели; у врача —
индивидуальный график и отсутствия. Все времена — в таймзоне клиники
(`clinic.timezone`, по умолчанию `Asia/Bishkek`).

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/clinic/schedule/day?date=&doctorId=` | Лента дня: сетка, обед, колонки врачей, карточки приёмов (`schedule.view_all` — все врачи; `schedule.view_own` — только своя колонка) |
| `GET` | `/clinic/schedule/slots?doctorId=&date=&serviceId=` | Свободные слоты врача с учётом часов, обеда, графика, отсутствий и занятости (`schedule.view_all` — любой врач; `schedule.view_own` — только `doctorId` = своё членство) |
| `GET` · `PUT` | `/clinic/schedule/working-hours` | Часы работы клиники, все 7 дней разом (`settings.view` / `settings.edit`) |
| `GET` · `PUT` | `/clinic/schedule/doctors/{id}/hours` | График врача, все 7 дней разом (`schedule.view_all`/`manage_all` — любой врач; `schedule.view_own`/`manage_own` — только своё) |
| `GET` · `POST` | `/clinic/schedule/doctors/{id}/time-off` | Отсутствия врача (отпуск/больничный): список и создание (`view_all`/`view_own`, `manage_all`/`manage_own`) |
| `DELETE` | `/clinic/schedule/doctors/{id}/time-off/{timeOffId}` | Снять отсутствие врача (`manage_all` — любой; `manage_own` — своё) |

> **Видимость «своё расписание».** Токен привязан к клинике, поэтому «свой» =
> собственное членство аккаунта в клинике из токена. С правами `*_own` (роль
> «работник») врач видит и правит только себя; `doctorId` **коллеги по клинике**
> → `403` `not_own_schedule` (это вопрос прав, а не тайны: коллег врач и так
> знает), а врач **чужой клиники** → `404` `doctor_not_found`, как и
> несуществующий. Собственный `membershipId` фронт берёт из `GET /auth/me`
> (`activeClinic.membershipId`). Не-практикующим (регистратор без специализации)
> для полной ленты выдают `schedule.view_all` на уровне роли.

> Приём занимает `[scheduledAt, scheduledAt + durationMin)`; длительность — из
> `durationMin`, иначе из `Service.duration`, иначе 30 мин. Пересечение приёмов у
> одного врача запрещено и в коде (409 `slot_taken`), и EXCLUDE-констрейнтом в БД
> (страховка от гонки — второй параллельный запрос тоже получит 409). Нерабочее
> время (вне окна, обед, отсутствие) → 422. Снятие отмены проходит проверку
> занятости заново: пока приём был отменён, слот мог достаться другому.
>
> **Запись вне графика.** `force: true` в `POST`/`PATCH` приёма (право
> `appointments.force_booking`, по умолчанию у владельца и менеджера) снимает
> **только** проверку рабочих часов и обеда: клиники принимают вне графика
> постоянно, и жёсткий запрет приводит лишь к тому, что приём не заведут в
> системе. Пересечение приёмов (409 `slot_taken`) и отпуск врача (422
> `doctor_time_off`) не обходятся никогда. Без права → 403
> `force_booking_forbidden`.
>
> `scheduledAt` **обязателен** у обычной записи: без даты → 422
> `scheduled_at_required`. Единственный приём без даты — черновик
> (`status: draft`). Дефолта «сейчас» нет намеренно: он превращал опечатку в
> имени поля в тихую запись «на текущий момент», а на повторной попытке отдавал
> 409 `slot_taken` — ошибку про занятость вместо «нет даты». Запись «прямо
> сейчас» никуда не делась: фронт шлёт текущее время явно.
>
> `scheduledAt` обязан нести **смещение таймзоны** (`2026-07-20T09:00:00+06:00`);
> время без смещения → 422. Иначе его пришлось бы трактовать по таймзоне сервера,
> и момент зависел бы от того, где запущено приложение (dev vs CI/прод в UTC).
> «Врач» везде одинаков — активное членство со специализацией.
>
> В `PATCH` **`null` допустим только для nullable-полей** (`doctorMembershipId`,
> `serviceId`, `comment`); для `status`/`appointmentType`/`scheduledAt`/`durationMin`
> → 422. `durationMin` — от 1 до 1440 минут. Снятие услуги (`serviceId: null`)
> длительность **не меняет**: приём на 90 минут не схлопывается до дефолтных 30 —
> нужна другая длительность, передайте `durationMin` явно.

**Клиническое ядро (клиент-сайд + RBAC).** Пациент **глобальный** (общий на всю
платформу, phone UNIQUE); клиника видит его при наличии приёма. История зуба —
**сквозная по всем клиникам**. Врач = наш `membership`.

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/clinic/patients` | Пациенты этой клиники (у кого есть приём), поиск/пагинация (`patients.view`) |
| `GET` | `/clinic/patients/lookup?phone=` | Глобальный поиск по телефону для привязки (`patients.edit`) |
| `POST` | `/clinic/patients` | Создать глобального пациента (409 с `patientId`, если телефон занят) |
| `GET` · `PATCH` | `/clinic/patients/{id}` | Карточка + одонтограмма + заметка (`note`) / правка (нужна связь с клиникой) |
| `PUT` | `/clinic/patients/{id}/teeth` | Создать/обновить одонтограмму (карта зубов, FDI) |
| `GET` | `/clinic/patients/{id}/teeth/{fdi}` | Сквозная история зуба (`patients.view_medical`) |
| `GET` · `POST` · `PATCH` | `/clinic/services[/{id}]` | Прайс клиники: список/создать/правка, включая `toothOutcome` (`price.view`/`price.edit`) |
| `GET` · `POST` | `/clinic/appointments` | Приёмы клиники (фильтр `status`) / создать со списком позиций (`items`), `serviceId`+`durationMin`; `status=draft` — черновик без даты, `force` — вне графика (`patients.view_medical`/`appointments.create`) |
| `GET` · `PATCH` | `/clinic/appointments/{id}` | Детали / обновить статус, перенести (`force`), пометить бесплатным (`noCharge`) (`patients.view_medical`/`appointments.edit`) |
| `PUT` | `/clinic/appointments/{id}/items` | Заменить позиции чека целиком и пересчитать итог (`appointments.edit`) |
| `PUT` | `/clinic/appointments/{id}/discount` | Скидка на приём процентом в пределах потолка роли (`cash.discount`) |
| `POST` | `/clinic/appointments/{id}/complete` | Завершить приём и опционально оплатить (одна транзакция; переплата откатывает); без позиций — только `noCharge` (`appointments.complete_pay`) |

> **Черновик приёма (`status=draft`).** Пациент заведён в клинику, но дату и
> услугу ещё не выбрал. Нужен потому, что клиника видит пациента только через
> наличие приёма — черновик добавляет человека в список пациентов, не занимая
> слот врача и не попадая в ленту дня и отчёты периода. Создаётся без
> `scheduledAt` (с датой → 422), достаётся фильтром `?status=draft` как список
> «кому перезвонить». Доводится до записи обычным `PATCH` (`scheduledAt` +
> `status`): без даты → 422 `scheduled_at_required`, занятый слот → 409, как при
> снятии отмены. Завершить черновик нельзя (422 `cannot_complete_draft`).
>
> Пустая дата легальна **только** у приёмов, которые не состоялись (`draft` и
> `cancelled`) — это стережёт CHECK `ck_appointment_scheduled_at_required` в БД,
> поэтому гарантия миграции 0020 (у рабочего приёма дата есть всегда) сохраняется.

**Приём = список позиций (чек).** Реальный приём почти всегда многопозиционный
(«кариес 36 + чистка»), поэтому в `items` их может быть сколько угодно:

| Поле позиции | Смысл |
|---|---|
| `serviceId` | Услуга из прайса; без неё цену задают вручную |
| `priceTiyin` | Цена **за единицу** на момент оказания; по умолчанию — цена услуги |
| `quantity` | Количество (1…999): «снимок ×3» — одна позиция, а не три |
| `teeth` | Номера зубов FDI: пусто (чистка, консультация) или несколько (мост на 35–37) |
| `status` | `planned` · `started` · `completed` · `cancelled` — что из плана реально сделали |
| `comment` | Пояснение к работе |

> Итог приёма `priceTotalTiyin` = Σ(`priceTiyin` × `quantity`) — его считает бэк,
> клиент не передаёт. Цена фиксируется в чеке: прайс потом меняется, а чек
> прошедшего приёма — нет. Отчёт «топ услуг» считает **количество**, а не число
> строк, иначе он занижает и работу, и выручку.
>
> **Правка чека** — `PUT /clinic/appointments/{id}/items`: передаётся полное
> состояние (как в часах работы клиники и одонтограмме), пустой список очищает.
> Что именно сделали, известно по ходу приёма, поэтому чек правится отдельно от
> статуса и даты. Завершённый приём — финансовый факт: 409 `appointment_completed`
> (меняют возвратом), у отменённого чека нет — 422. Итог ниже уже оплаченного →
> 422 `total_below_paid`: сначала возврат, иначе в кассе появится приём с
> отрицательным долгом.
>
> **Привязка к зубам** живёт в связке «позиция ↔ зуб», поэтому одна работа на
> несколько зубов попадает в сквозную историю **каждого** из них.
>
> **Одонтограмма догоняет историю.** У услуги есть `toothOutcome` — в какое
> состояние она приводит зуб («Пломба» → `filling`, «Коронка» → `crown`,
> «Удаление» → `missing`). При завершении приёма карта зубов обновляется сама по
> сделанным позициям: вылеченный зуб перестаёт числиться кариозным без ручной
> правки через `PUT /clinic/patients/{id}/teeth`.
>
> `toothOutcome: null` (по умолчанию) — услуга состояние зуба не меняет (чистка,
> консультация, снимок). Выводить исход из НАЗВАНИЯ услуги нельзя: прайс ведёт
> клиника, и «Реставрация II класса» ничему не подскажет — поэтому до настройки
> прайса синк просто не срабатывает. Отменённые позиции карту не трогают, а если
> в одном приёме зуб сначала запломбировали, потом удалили — побеждает последняя
> позиция чека.
>
> **Статус позиции** по умолчанию `planned`. Завершение приёма (и ручкой, и
> `PATCH status: completed`) само доводит `planned`/`started` до `completed`, а
> `cancelled` не трогает: врач уже сказал, что этого не делал. Иначе статус
> остался бы вечным `planned` — построчно проставлять его на каждом закрытии
> никто не станет. Виден в карточке приёма и в истории зуба.

**Скидка — право + потолок роли.** Скидка единственная операция, где сотрудник в
одиночку уменьшает выручку, поэтому «можно» и «сколько» разведены:

| Уровень | Что задаёт | Где |
|---|---|---|
| Право `cash.discount` | можно ли давать скидку вообще | набор прав роли |
| `maxDiscountPercent` | насколько (владелец 100, администратор 20, врач 0) | поле роли, правится в `PATCH /clinic/roles/{id}` |

> `PUT /clinic/appointments/{id}/discount` c `{"percent": 10}`; `0` снимает
> скидку. Сверх потолка → 403 `discount_limit_exceeded` с полем
> `maxDiscountPercent`. Каждая скидка пишется в аудит (`appointment.discount`).
>
> В чеке видно всё: `subtotalTiyin` (сумма позиций), `discountPercent`,
> `discountTiyin` и `priceTotalTiyin` — **итог к оплате**, по нему же считается
> долг кассы. Скидка пересчитывается при правке позиций: процент относится к
> текущей сумме, а не к той, что была. Опустить итог ниже уже оплаченного нельзя
> (422 `total_below_paid`), завершённому приёму скидку не дают (409). Сколько
> клиника раздала за период — `discountsTiyin` в `GET /clinic/reports/summary`.

**Жизненный цикл приёма.** Восемь статусов:

```
draft → scheduled → confirmed → arrived → in_progress → completed
                 ↘ cancelled (+ cancelReason) / no_show ↙
```

| Статус | Что значит |
|---|---|
| `draft` | Пациент заведён, дата не выбрана |
| `scheduled` | Запись создана, пациент ещё не подтвердил |
| `confirmed` | Пациент подтвердил (например, ответом в WhatsApp) |
| `arrived` | Пришёл в клинику, ждёт врача |
| `in_progress` | Идёт приём (пациент в кресле) |
| `completed` | Завершён (и оплачен, если платёж проведён) |
| `cancelled` | Отменён; причина — в `cancelReason` |
| `no_show` | Не пришёл |

**Переходы валидируются** и делятся на два класса.

**Вперёд по воронке** — обычная работа, ничего не требует (в том числе
«перепрыгнуть»: записали и сразу закрыли приём).

**Откат назад** — узкий и подотчётный, всё сразу:

| Требование | Иначе |
|---|---|
| Ровно один шаг назад (плюс `no_show → scheduled\|arrived`, `cancelled → scheduled`) | 409 `invalid_status_transition` |
| Право `appointments.status_rollback` (владелец, менеджер; врачу не выдаётся) | 403 `status_rollback_forbidden` |
| Приём **текущего дня** | 422 `rollback_not_today` |
| `rollbackComment` — попадает в аудит | 422 `rollback_comment_required` |

> **`completed` терминальный.** Ошибочно закрытый приём исправляется **возвратом
> платежа**, а не откатом статуса: завершённый приём — финансовый факт, он уже в
> кассе и в выручке врача.

**Причина отмены — справочником** (`cancelReason`), обязательна при
`status: cancelled` (иначе 422 `cancel_reason_required`) и запрещена без неё:
`patient_request`, `patient_illness`, `clinic_reschedule`, `doctor_unavailable`,
`duplicate`, `other`. При `other` обязателен `cancelComment` (422
`cancel_comment_required`). При снятии отмены оба поля очищаются.

**Отмена обнуляет сумму, позиции остаются.** Прерванный приём (в том числе из
`in_progress`) сохраняет позиции чека — это часть истории зуба, — но
`priceTotalTiyin` становится `0`: денег за несостоявшийся приём не берут. Иначе
такие случаи закрывают как `completed` с нулём, то есть врут отчёту. Снятие
отмены пересчитывает итог **из позиций**, а не возвращает запомненное число.

**Закрыть приём без позиций нельзя** — ни `POST .../complete`, ни `PATCH`
со `status: completed`: иначе нулевые чеки копятся и портят среднюю выручку.

| Требование | Иначе |
|---|---|
| Есть хотя бы одна позиция (`teeth`) либо флаг `noCharge` | 422 `appointment_without_items` |
| При `noCharge: true` — пояснение `noChargeComment` | 422 `no_charge_comment_required` |
| `noCharge` — только у приёма **без** позиций | 422 `no_charge_with_items` |
| `noChargeComment` — только вместе с флагом | 422 `no_charge_comment_without_flag` |

> Бесплатный приём (гарантийный осмотр, доработка) бывает — но он должен быть
> решением с пояснением, а не следствием незаполненной формы. Флаг можно
> проставить заранее обычным `PATCH`: тогда в теле завершения его не повторяют.
> Скидку флаг не заменяет — приём с позициями им не обнуляется.

**Касса клиники (клиент-сайд + RBAC).** Оплата приёмов пациентами. Долг считается
по приёму: `остаток = priceTotalTiyin − Σплатежей + Σвозвратов`.
«Своё» = собственное членство в клинике из токена (для платежей — кто провёл, для
долгов — лечащий врач).

| Метод | Путь | Описание |
|---|---|---|
| `GET` · `POST` | `/clinic/cash/payments` | Журнал (view_all → вся клиника, view_own → свои) / провести платёж (`cash.operate`); переплата → 422 |
| `POST` | `/clinic/cash/payments/{id}/refund` | Возврат по платежу: частичный (`amountTiyin`) или остаток; сверх остатка → 422, по исчерпанному → 409 (`cash.operate`) |
| `GET` | `/clinic/cash/summary?from=&to=` | Приход/возврат/нетто по способам оплаты (`cash.view_all`/`view_own`) |
| `GET` | `/clinic/cash/debts?patientId=` | Завершённые приёмы с ненулевым остатком (`cash.view_all`/`view_own`) |

> **Возврат частичный и многократный.** «Из трёх услуг переделали одну» —
> обычный случай, поэтому по одному платежу может быть несколько возвратов;
> ограничение одно: их сумма не больше самого платежа. `amountTiyin` не передан
> — возвращается весь остаток (привычный полный возврат). Сверх остатка → 422
> `refund_exceeds_payment` с полем `refundableTiyin`; когда возвращать нечего →
> 409 `already_refunded`. Возврат по возврату запрещён (422 `not_a_payment`):
> сторнируют приход. Каждая строка журнала несёт `refundedTiyin` и
> `refundableTiyin`, а возврат — `refundsPaymentId`, чтобы фронт не пересобирал
> остаток сам.

**Настройки клиники (клиент-сайд).** Клиника ведёт себя сама; тариф ведёт Skrezo.

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/clinic/settings` | Название, город, адрес, телефон, язык, таймзона + тариф только на чтение (`settings.view`) |
| `PATCH` | `/clinic/settings` | Правка перечисленного (`settings.edit`) |

> **Таймзона** — самое ответственное поле: в ней считаются лента дня, свободные
> слоты и границы периодов в отчётах. Неизвестная зона отвергается (422
> `invalid_timezone`), а не откатывается молча на `Asia/Bishkek` — иначе
> расписание уедет, и в интерфейсе это ни с чем не свяжут. `type`, `seatsLimit`
> (тариф) и заметки саппорта через эту ручку не меняются и в выдаче настроек
> не появляются.

**Подписка клиники (клиент-сайд, право `billing.view`).** Клиника из токена —
чужую подписку по этой ручке не посмотреть.

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/clinic/subscription` | Статус, срок (`expiresAt`), остаток дней (`daysLeft`), флаги `isTrial`/`expired` |

> **На 31-й день клиника переходит в режим ЧТЕНИЯ.** Мутирующие операции
> (запись на приём, касса, правки, настройки) отвечают 403
> `subscription_inactive`; чтение — списки, карточки, расписание, отчёты — живо,
> как и `billing.*`: им клиент и продлевает доступ. В ответе подписки это поле
> `writesBlocked`, в `/auth/me` мутирующие права из списка исчезают — фронту
> прятать кнопки.
>
> Доступ считается **по датам** (`trialEndsAt` для триала, `currentPeriodEnd`
> для оплаченного периода), а не по статусу в БД: статус переводит фоновая
> джоба, и завязка на неё означала бы, что упавший воркер раздаёт бесплатный
> доступ. Джобы (arq, ежечасно) переводят `trial` → `trial_expired` и
> `active` → `past_due` и пишут событие — чтобы админка и дашборд не показывали
> должника активным клиентом. Состояние подписки кешируется 30 секунд: столько
> после конца срока записи ещё проходят.
>
> ⚠️ Симметрия здесь не для красоты. Раньше по дате считался только триал, а
> оплаченный период — по статусу: клиника с давно кончившимся периодом сохраняла
> полный доступ, пока кто-нибудь не сменит ей статус вручную.
>
> Тот же режим чтения включают `awaiting_card`, `past_due`, `blocked` и
> `cancelled`.
>
> **Оплата отмечается вручную.** Платёжного провайдера нет, клиники платят
> переводом на счёт: команда Skrezo вызывает
> `POST /admin/clients/{id}/subscription/activate` с `paidUntil` — подписка
> становится `active` до этой даты, кеш состояния сбрасывается, и клиника
> получает доступ сразу, а не через полминуты. Суммы ручка не принимает:
> журнала платежей ещё нет, и класть её некуда. `.../block` закрывает запись
> решением Skrezo — последствия те же, но по статусу видно, что дело не в оплате.
>
> Перед концом срока владельцу приходит предупреждение — и по триалу, и по
> оплаченному периоду (`TRIAL_WARNING_DAYS`, по умолчанию 3 дня). Отметка
> «предупредили» у периода **сбрасывается при каждом продлении**: иначе клиент
> получил бы её один раз за всю жизнь, а дальше узнавал бы о конце оплаты в
> момент, когда касса встала.
>
> Без ручки соло-врачу обещаны 30 дней, а на 31-й день не происходит ничего:
> клиент не может показать ни срок, ни повод продлить. `expiresAt` — конец
> триала (`trialEndsAt`) либо конец оплаченного периода; `daysLeft: 0` означает
> «идёт последний день либо срок вышел», признак истечения — `expired`. Право
> `billing.view` разумно оставлять доступным на триале (`/admin/trial-features`),
> иначе именно те, кому ручка нужнее всего, получат 403.

**Роли и права (клиент-сайд, право `roles.manage`).** Клиника настраивает свои
роли: системные (владелец/менеджер/работник) клонируются при создании клиники,
поверх можно завести кастомные.

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/clinic/roles` | Роли клиники с правами, числом сотрудников и флагами `editablePermissions`/`deletable` |
| `GET` | `/clinic/permissions` | Каталог прав (ключ, `groupKey`, описание) — чекбоксы конструктора роли |
| `POST` | `/clinic/roles` | Создать кастомную роль (название + набор прав) |
| `PATCH` | `/clinic/roles/{id}` | Переименовать, **заменить набор прав целиком** и/или задать потолок скидки |
| `DELETE` | `/clinic/roles/{id}` | Удалить кастомную роль |

> **Инварианты.** Роль владельца не редактируется (полный доступ всегда) → 409
> `owner_role_immutable`. Системным ролям права правятся пер-клиника, но
> переименование (`system_role_rename`) и удаление (`system_role_delete`)
> закрыты. Роль с активными сотрудниками не удалить → 409 `role_has_members`.
> Изменение прав применяется **сразу** — кеш `PermissionResolver` сбрасывается.
> По умолчанию `roles.manage` есть только у владельца. Роль сотрудника
> назначается при найме (`roleId` в `POST /clinic/staff`) или меняется потом
> (`PUT /clinic/staff/{id}`); роль владельца не назначается — он в клинике один.
> У каждой роли есть `maxDiscountPercent` — потолок скидки (см. ниже).

**Отчёты клиники (клиент-сайд + RBAC).** Операционная аналитика поверх кассы и
приёмов. Период — пресет `period=7d|1m|3m|all` (по умолчанию `1m`) либо произвольный
`from`/`to` (перекрывает пресет), границы считаются в таймзоне клиники. Деньги
берутся по дате платежа, приёмы и производное от них — по дате приёма.

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/clinic/reports/summary` | Всё для экрана: выручка (+ по способам), приёмы по статусам, пациенты новые/повторные, начислено, **скидки**, долг, средний чек |
| `GET` | `/clinic/reports/revenue?groupBy=day\|month` | Динамика выручки |
| `GET` | `/clinic/reports/doctors` | По врачам: приёмы, завершено/отменено, начислено, оплачено, долг, средний чек |
| `GET` | `/clinic/reports/services` | Топ услуг: сколько раз оказана (с учётом количества) и выручка |

> `reports.view_all` (владелец/менеджер) — вся клиника; `reports.view_own` (врач) —
> **все** разрезы сужаются до приёмов, где он лечащий врач (в отчёте по врачам
> остаётся одна строка). Это «своё» отличается от кассы, где «своё» = кто провёл
> платёж: отчёт врача — про его работу, а не про приём денег.

**Отчёты по клиникам (Skrezo).** Платформенный контур, только `is_platform_admin`,
без ограничений по врачу.

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/admin/reports/clinics` | Свод по всем клиникам (выручка, долг, приёмы, врачи, пациенты) — экран выбора клиники |
| `GET` | `/admin/reports/clinics/{id}/summary·revenue·doctors·services` | Тот же набор отчётов по выбранной клинике |

**Защита (rate-limit).** На Redis, фиксированное окно, 429 `too_many_requests` с
`retryAfter`: вход (`/auth/login`, по IP+телефон), смена пароля, выпуск кода
(`/auth/otp/request` и `/auth/password/forgot` — счётчики раздельные), сам сброс
пароля, лид-форма (по IP). Лимиты — в переменных окружения (`LOGIN_RATE_LIMIT` и др.).

> **Три пути смены пароля.** Своим текущим паролем — `/auth/change-password`;
> самостоятельно по коду из сообщения — `/auth/password/forgot` + `/reset`;
> чужими руками (Skrezo владельцу, владелец работнику) — ручки `reset-password`,
> они выдают новый временный пароль. Третий путь нужен, когда номер сменился и
> код прислать уже некуда.
>
> Код на смену пароля и код на вход — **разные коды**: они лежат под разными
> ключами и не взаимозаменяемы. Иначе «продиктуйте код из SMS» открывало бы
> не только вход, но и смену пароля.
>
> Успешный сброс отзывает refresh-сессии аккаунта. Выданные ранее access-токены
> доживают свой короткий TTL — мгновенный отзыв потребовал бы проверки версии
> токена на каждом запросе.
>
> `patientsCount`, `revenueTiyin` и блок `activity` в карточке клиента считаются
> из клинического ядра и кассы клиники. ⚠️ `revenueTiyin` — оборот САМОЙ клиники;
> сколько она заплатила Skrezo, это `lifetimeRevenueTiyin`.
>
> Отложено (зависит от биллинга): `POST /admin/billing/pay-now`, экспорт платежей
> `GET /admin/payments/export`, метрики `mrr`/`lifetimeRevenue` и журнал
> `payments` в карточке — пока нули и пустые списки.
| `GET` | `/api/v1/admin/audit` | Журнал аудита (фильтры actor/clinicId/from/to) |
| `GET` · `PATCH` | `/admin/trial-features` | Набор прав, доступных на триале: список и пакетная настройка (`inTrial`) |
| `GET` | `/admin/clinic-applications` | Заявки клиник: фильтр `status`, пагинация, `statusCounts` для бейджей |
| `GET` | `/admin/clinic-applications/{id}` | Карточка заявки (компания, город, размер, телефон, кто рассмотрел) |
| `PATCH` | `/admin/clinic-applications/{id}/status` | Статус: `pending` \| `reviewed` \| `rejected` (пишется в аудит) |

> **Триал-функции.** Клиника на 30-дневном триале использует только права с
> `permission.in_trial = true`. По умолчанию доступно всё — админ выключает
> ненужное из `/admin/trial-features`; ограничение (`403 trial_restricted`)
> применяется сразу и покрывает все контуры (`require_permission` и
> скоуп-guard'ы расписания/кассы/отчётов), включая владельца.

Создать админа Skrezo: `make create-admin phone=0700000001 password=secret`.
Тестовая клиника (dev): `uv run python -m app.scripts.create_test_clinic --phone 0700123456`.

## Фоновые задачи (воркер)

Отдельный процесс на **arq**: `make worker` локально, сервис `worker` в
`docker-compose.yml`. Задачи двух родов.

**По расписанию** — идемпотентны, arq их не повторяет (`max_tries=1`): повтор по
графику безопаснее ретрая поверх недоделанного.

| Задача | Когда | Что делает |
|---|---|---|
| `expire_trials` | ежечасно, :05 | `trial` → `trial_expired` + сообщение владельцу и сводка в чат команды |
| `expire_paid_periods` | ежечасно, :10 | `active` с истёкшим периодом → `past_due` + сообщение владельцу и сводка в чат |
| `warn_trial_ending` | ежедневно, 03:15 UTC (09:15 Бишкек) | «Триал кончается через N дней» владельцу и в чат; однократно на клинику |
| `warn_period_ending` | ежедневно, 03:20 UTC | То же про оплаченный период; отметка сбрасывается при каждом продлении |
| `cleanup_job_runs` | ежедневно, 02:30 UTC | Удаляет журнал старше `JOB_RUN_RETENTION_DAYS` |
| `heartbeat` | ежеминутно и на старте | Отметка «воркер жив» в Redis (в журнал не пишется) |

**По событию** — ставятся из обработчика запроса: `send_notification` (телефон,
цепочка каналов) и `send_team_notification` (чат команды). Их как раз повторять
нужно — провайдер мог не ответить: до 5 попыток с растущей задержкой.

> **Постановка задачи из API.** Пул arq открывается в lifespan приложения. Если
> он недоступен (Redis лёг; в тестах lifespan не запускается вовсе), отправитель
> уведомлений это видит и шлёт сообщение **на месте** — потерять уведомление
> хуже, чем задержать ответ. В логе такой путь виден как `notification_sent_inline`.
>
> **Однократность предупреждения** держится не на памяти джобы, а на запросе:
> отметка `subscription.trial_warning_sent_at` ставится тем же `UPDATE`, который
> отбирает клиники. Раздельные SELECT и UPDATE прислали бы второе сообщение при
> двойном запуске (ретрай, второй воркер).

**Состояние воркера** — `GET /admin/jobs`: признак `alive` (по отметке жизни в
Redis) и последний запуск каждой задачи; журнал — `GET /admin/jobs/runs`.
Каждый запуск пишется в таблицу `job_run` дважды: `running` при старте и исход
при завершении. Иначе убитая на полпути задача не оставляла бы следа, а именно
её и нужно заметить. Журнал пишется **отдельной сессией**: у упавшей задачи
транзакция откатывается, и запись о падении откатилась бы вместе с ней.

> `alive: false` значит, что триалы не закрываются, предупреждения не уходят, а
> сообщения копятся в очереди. Задачи, которая ни разу не запускалась, в
> `lastRuns` не будет вовсе — это отдельный симптом, по логам он не виден.

## Мультиязычность

Языки: `kg`, `kz`, `ru`, `en` (дефолт `ru`). Язык ответа: `?lang=en` или заголовок
`Accept-Language`. Пример: `GET /api/v1/cities?lang=en` → `Bishkek`; без параметра
→ `Бишкек`. Названия справочников — в таблицах переводов; `ru`/`en` заполнены,
`kg`/`kz` — заглушки под вычитку носителями.

## Формат ответа и ошибок

Успех — тело ресурса как есть. Ошибка — «плоский конверт»:

```json
{ "error": "lead_already_exists", "message": "...", "createdAt": "..." }
```

> **Чужое — это 404, а не 403.** Всё, что принадлежит другой клинике (пациент без
> приёмов у вас, приём, платёж, врач, роль, сотрудник), отвечает ровно так же,
> как несуществующее: `404` с тем же телом. Иначе перебором идентификаторов
> подтверждается существование чужих пациентов — «403» читается как «такой есть,
> но не ваш». Привязка нового пациента идёт другим путём —
> `GET /clinic/patients/lookup?phone=` по ТОЧНОМУ номеру.
>
> `403` остаётся там, где речь о правах внутри своей клиники: нет права
> (`Недостаточно прав`), функция закрыта на триале (`trial_restricted`), врач
> просит расписание коллеги (`not_own_schedule`), скидка сверх потолка роли
> (`discount_limit_exceeded`).

  push в `main` и PR (Docker на `ubuntu-latest` доступен для testcontainers).

## Структура проекта

Строгие конвенции DDD: **presentation → application → infrastructure → domain**,
все **ORM в `shared/db/models`** (одна таблица = один файл), доступ — через
репозитории. Подробнее — [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) §2, §8.

```
app/
  core/                 # config, db, redis, security(JWT), errors, logging
  shared/
    db/models/          # ВСЕ ORM-модели, по файлу на таблицу (account.py, city.py, …)
    db/base.py|enums.py # Base, миксины, enum-типы (Lang, ClinicType)
    i18n/               # резолв языка запроса + каталог сообщений
    api/                # базовые схемы (CamelModel)
    notifications/      # транспорты сообщений (WhatsApp, SMS, чат) + фоновая отправка
  modules/<module>/
    presentation/       # routes/ (1 эндпоинт = 1 файл), schemas.py, deps.py
    application/        # use_cases/ (1 задача = 1 use_case), services/
    infrastructure/     # repositories/ (доступ к данным поверх shared ORM)
    domain/             # enums, доменные данные (не ORM)
  jobs/                 # arq-воркер: расписание и запуск задач (работа — в модулях)
alembic/                # миграции
docs/                   # ARCHITECTURE.md
```

Реализованные модули: `catalog` (справочники, i18n), `access` (RBAC),
`platform_auth` (вход Skrezo). Остальные — по фазам.
