# Пуш-уведомления (сервер → приложение) — план и архитектурное решение

> Статус: **черновик к обсуждению**. Готов к разбивке на задачи.
> Источник требований: `WHATSAPP_AI.md` не покрывает — здесь только пуш-контур
> из `PUSH_CATALOG.md` (фронт-спецификация «как надо»).
> Дата: 2026-08-25.

---

## 1. Контекст

Сегодня уведомления о приёмах планируются **на телефоне**: приложение читает
день и само раскладывает будильники. Это ломается на первом расхождении — запись
подвинули с другого устройства, телефон об этом не знает и напомнит о приёме,
которого уже нет.

Задача — перенести источник события туда, где меняются данные (на сервер), и
доставлять его пушем через FCM (Android) и APNs (iOS).

### Что уже есть (фора)

| Компонент | Где | Как переиспользуем |
|---|---|---|
| Статусы приёма `draft/scheduled/confirmed/arrived/in_progress/completed/cancelled/no_show` | `app/shared/db/enums.py` | Каталог пушей завязан ровно на них — менять не нужно |
| Очередь **arq**: `JobQueue.enqueue(name, *args, job_id=, defer_by=)` | `app/core/jobs.py` | `job_id` = идемпотентность, `defer_by` = отложенные пуши |
| Воркер + cron + журнал `job_run` + `JobRunRecorder` | `app/jobs/` | Планировщик сводок и скан «пора напомнить» |
| `clinic.timezone` (Asia/Bishkek), `clinic.lang` | `app/shared/db/models/clinic.py` | Часовой пояс клиники для сводок и тихих часов |
| i18n kg/kz/ru/en | `app/shared/i18n/` | Серверные тексты пушей |
| RBAC: роли + членство, токен несёт `account_id + clinic_id + role_id` | `app/shared/auth/context.py` | Маршрутизация «кому» через членство |
| Паттерн роутов `/clinic/*` с `require_permission` + `AuditService` | `app/modules/clinics/presentation/routes/` | Шаблон для `/clinic/devices`, `/clinic/notifications/prefs` |

### Чего нет вообще (объём работы)

- Транспорт FCM + APNs — ноль.
- Таблицы `device`, `notification_pref`.
- Эндпоинты регистрации устройств и префов.
- Слой **dispatch** «доменное событие → пуш» (идемпотентность, collapse, i18n,
  часовой пояс, тихие часы, маршрутизация по ролям).
- Планировщик пушей, привязанных ко времени (`soon` −15 мин, `arrival` +5 мин).
- Точки эмиссии событий в существующих use-case'ах.

## 2. Границы: сервер vs приложение

- **Текст готовит сервер** (`title/body/speak`), из каталога сообщений по
  `locale` устройства. Генератор в приложении (`texts.ts`) остаётся фолбэком на
  пустой `title`.
- **Идемпотентность и схлопывание — на сервере**: сервер выдаёт стабильный
  `data.id` и `collapseKey`. Пуш нельзя отозвать ни на одной платформе —
  «снятие» неактуального делается через `sync.day`, приложение само убирает своё
  локальное уведомление.
- **Часовой пояс — клиники, не устройства.** Врач в отпуске в другом поясе не
  должен получать утреннюю сводку в 4 утра.
- **Никаких медданных в тексте.** Имя, дата, время, сумма — предел. Диагнозы,
  жалобы, снимки в пуш не уходят никогда (экран блокировки видят посторонние).

## 3. Архитектура

### 3.1. Размещение кода (DDD)

- **`app/shared/push/`** — транспорт (аналог существующего `shared/notifications`
  для текста): клиенты FCM и APNs, общая форма payload, обработка `NotRegistered`.
  Отдельно от `shared/notifications`, чтобы не путать «текст на телефон пациента»
  (OTP/SMS) с «пуш в приложение врача».
- **`app/modules/push/`** — доменный модуль:
  - `domain/` — типы событий (каталог), спецификация получателя, префы;
  - `infrastructure/` — репозитории `device`, `notification_pref`, `push_event`;
  - `application/` — `PushDispatcher` (событие → устройства → доставка), рендер
    текста из каталога, применение префов и тихих часов;
  - `presentation/routes/` — `/clinic/devices`, `/clinic/notifications/prefs`.
- **`app/jobs/tasks/push.py`** — тонкие arq-адаптеры: `dispatch_push` (по
  событию, retryable) и cron-сканы (`scan_due_appointments`, `send_digests`).

> ⚠️ Именование: у нас уже есть `shared/notifications` (текст/OTP). Новый
> транспорт — `shared/push`, доменный модуль — `push`. Не смешивать.

### 3.2. Новые таблицы

**`device`** — токен устройства, привязан к членству (account + clinic).

| Поле | Тип | Заметка |
|---|---|---|
| `id` | uuid pk | |
| `account_id` | fk account | |
| `clinic_id` | fk clinic | членство = (account, clinic); события одной клиники не идут, пока человек в другой |
| `token` | text **unique** | протухает молча |
| `platform` | enum `ios`/`android` | новый enum `DevicePlatform` |
| `app_version` | text nullable | |
| `locale` | enum `Lang` | язык текста пуша |
| `created_at`, `last_seen_at` | timestamptz | `last_seen_at` обновляется при повторной регистрации |

- Один человек — несколько устройств.
- `NotRegistered`/`Unregistered` от FCM/APNs → **удалить токен без ретраев**.

**`notification_pref`** — префы на членство.

| Поле | Тип | Заметка |
|---|---|---|
| `account_id`, `clinic_id` | fk, **уникальны вместе** | одна строка на членство |
| `disabled` | text[] | список отключённых `type` |
| `quiet_from`, `quiet_to` | time nullable | тихие часы по времени клиники |

- Отсутствие строки = дефолт (ничего не отключено, тихих часов нет).
- Группу `subscription.*` **нельзя отключить** — проверка на уровне dispatch, а
  не UI.

**`push_event`** (идемпотентность и журнал) — минимально.

| Поле | Тип | Заметка |
|---|---|---|
| `id` | text pk | = `data.id` (`evt_...`), стабильный |
| `type` | text | |
| `clinic_id` | fk | |
| `dedup_key` | text | = `collapseKey`; для скана «уже слали?» |
| `created_at` | timestamptz | |

> MVP-упрощение: для событий, порождённых напрямую из запроса, идемпотентность
> даёт `job_id` в arq (повторная постановка с тем же id — no-op). `push_event`
> нужен там, где событие ищет **скан по расписанию** (`soon`/`arrival`/сводки):
> флаг «этому приёму этот пуш уже слали».

### 3.3. Эндпоинты (приложение → сервер)

```
POST   /api/v1/clinic/devices              { token, platform, appVersion, locale }
DELETE /api/v1/clinic/devices/{token}
PUT    /api/v1/clinic/notifications/prefs   { disabled[], quietFrom, quietTo }
```

- Guard: любой аутентифицированный член клиники (не `settings.edit` — устройство
  и префы **свои**, привязка через `context.account_id + context.clinic_id`).
- Токен снимается на выходе из приложения (logout) и на `NotRegistered`.

### 3.4. Слой доставки (транспорт)

- **FCM HTTP v1** — авторизация OAuth2 через service-account JSON.
- **APNs** — token-based (`.p8` ключ, key id, team id, bundle id), sandbox/prod.
- Оба — async `httpx`, свой таймаут.
- Общая форма payload — как в `PUSH_CATALOG.md` §1: `notification` + `data`
  (`type`, `id`, `clinicId`, `appointmentId`, `patientName`, `startsAt`, `speak`,
  `category`) + платформенные блоки (`android.priority/channelId`,
  `apns.headers` + `interruption-level` + `category`).
- Новые переменные окружения (секреты): FCM service account, APNs key/ids, среда.
- **Лог-фолбэк, пока кредов нет (решено).** Кредов FCM/APNs сейчас нет —
  транспорт config-driven: если ключи пустые, работает `LoggingPushChannel`
  (пуш пишется в лог, ничего не падает), по аналогии с `logging_channel.py` для
  OTP. Реальные каналы включаются заполнением конфига без правок кода.

### 3.5. Слой dispatch (событие → пуш)

`PushDispatcher.dispatch(event_type, clinic_id, context_ids, recipients_spec)`:

1. **Резолв получателей** → членства → устройства (см. §3.6).
2. **Префы**: отфильтровать `disabled`; тихие часы → `digest`-события
   отложить до утра, срочные (`appointment.*`, `subscription.expired`) слать
   всегда. `subscription.*` игнорирует `disabled`.
3. **Рендер текста** `title/body/speak` из каталога по `locale` устройства.
4. **Стабильный `data.id`** и `collapseKey` (= `appointmentId + type`).
5. Поставить задачу доставки на **каждое устройство** (retryable).

**Точка вызова — из use-case'а после коммита** (дисциплина проекта: инвалидация
кеша / эмиссия событий строго после `commit`, иначе гонка «пуш ушёл, транзакция
откатилась»). Практически: use-case вызывает `JobQueue.enqueue("dispatch_push",
descriptor, job_id=stable_id)` — в очередь кладётся **дескриптор события**, а не
готовый payload. Причины:

- текст и получатели считаются в момент отправки → не устаревают;
- логика в одном месте, а не размазана по use-case'ам;
- переживает рестарт воркера, есть ретраи из коробки;
- если пул очереди недоступен (тесты, Redis лёг) — `enqueue` вернёт `False`,
  и это ок: пуш не критичен для консистентности данных.

### 3.6. Маршрутизация «кому»

| Спецификация | Как резолвится |
|---|---|
| Врач приёма | членство `appointment.doctor_membership` |
| Владелец | членства с ролью `owner` |
| Ресепшен | **= роль `manager`** (решено) |
| Деньги | владелец + менеджер (`owner` + `manager`), **не врач** |

**Нет менеджера — получает владелец** (решение 17.10.2026). События, адресованные
только менеджеру (`ai.escalated`, `ai.draft_ready`, `conversation.waiting`,
`conversation.inbound`, `appointment.status_changed`), в клинике без живого
менеджера уходят владельцу. Иначе у соло-врача и в небольшой клинике «пациент
ждёт человека» не доходил ни до кого: событие обработано, инбокс и пуш пусты.
Если менеджер есть, владельца такими событиями не беспокоим.

### 3.7. Планировщик времязависимых пушей

**Решение: cron-скан раз в минуту, а не отложенные задачи.** `soon` (−15 мин) и
`arrival` (+5 мин) — это `scan_due_appointments`, который берёт приёмы, попавшие
в окно, у которых статус ещё `scheduled/confirmed` и по `push_event` пуш ещё не
слали.

Почему скан, а не `defer_by`:

- **Не слать, если статус уже изменил сам врач** — скан проверяет статус в момент
  отправки, отложенная задача этого не знает без отмены;
- перенос/отмена приёма не требуют отменять ранее поставленную задачу (арк не
  умеет надёжно заменять `job_id` с новым `defer_by`);
- черновики (`scheduled_at = NULL`) скан пропускает фильтром.

Альтернатива (`defer_by` + `job_id = f"{appointmentId}:soon"` + отмена при
переносе) — сложнее и хрупче. Скан выбран.

**Сводки** (`day.morning` 7:30, `day.evening` 19:00, `cash.dayClosed` 20:00) —
тоже cron-скан, с фильтром «непустой день» (нулевой день не шлём — это шум).

**Мультитаймзонность — сразу (решено).** Cron бьётся раз в минуту и для каждой
клиники считает локальное время по `clinic.timezone`; сводка уходит тем, у кого
локально наступил целевой час. Не хардкодим Asia/Bishkek под единый UTC-cron —
так не придётся переделывать при первой клинике в другом поясе.

### 3.8. `sync.day` — тихий пуш (приоритет №1)

- Без `notification`, только `data`, `content-available: 1` на iOS.
- Шлётся на **любое** изменение расписания клиники на сегодня/завтра —
  фан-аут на все устройства членств клиники.
- Приложение по нему перечитывает день. iOS режет частоту тихих пушей — поэтому
  `sync.day` **дополняет** видимые пуши §2 каталога, а не заменяет их.

## 5. Сквозные правила (заложить сразу)

1. **Идемпотентность** — `data.id` уникален и стабилен; повтор с тем же id
   приложение игнорирует. На стороне сервера — `job_id` (событие из запроса) или
   `push_event` (скан).
2. **Схлопывание** — `collapseKey = appointmentId + type`. Приём двигали трижды —
   врач видит последнее состояние, а не три пуша.
3. **Отзыв** — через `sync.day`, не напрямую (нельзя ни на одной платформе).
4. **Часовой пояс клиники**, не устройства.
5. **i18n** — `locale` с токена устройства; тексты RU и KG (минимум).
6. **Никаких медданных** — имя + время + сумма предел.
7. **Тихие часы** — копятся только `digest`; срочные идут всегда.
8. **NotRegistered → удалить токен**, без ретраев.

## 6. Решения (закрыто 2026-08-25)

1. **Роль «ресепшен» = `manager`.** Отдельную роль не заводим; получатели
   «ресепшен»/деньги = `owner` + `manager`.
2. **Мультитаймзонность — строим сразу.** tz-aware минутный скан по
   `clinic.timezone` (см. §3.7), не единый UTC-cron.
3. **Тексты и `speak` — редактируемый конфиг-каталог.** Формулировок пока нет;
   заводим `app/modules/push/domain/catalog.py` со структурой на все `type` ×
   `Lang` × (`title`/`body`/`speak`) и плейсхолдерами (`{patientName}`, `{time}`,
   `{amount}`). Владелец дополняет тексты позже правкой одного файла; пустой
   `title` → приложение берёт свой фолбэк (`texts.ts`).
4. **APNs/FCM аккаунтов ещё нет.** Транспорт делаем config-driven с лог-фолбэком
   (см. §3.4): без кредов система работает и логирует, включение — заполнением
   конфига. Нужные секреты завести позже: service-account JSON (FCM), `.p8` +
   key id + team id + bundle id (APNs).

## 7. Разбивка на этапы (порядок из каталога: от самого полезного)

- **P0 — Фундамент.** Транспорт FCM+APNs (+ фейк для тестов), config/секреты,
  таблицы `device`/`notification_pref`/`push_event` + миграция, эндпоинты
  `/clinic/devices`, `/clinic/notifications/prefs`. Каркас `PushDispatcher`.
- **P1 — `sync.day`.** Эмиссия из мутаций расписания/приёмов, тихий фан-аут.
  Закрывает главную дыру.
- **P2 — `appointment.arrival` + `appointment.soon`.** Cron-скан, каталог
  текстов, collapse/идемпотентность, «не слать, если статус тронут».
- **P3 — `appointment.moved` / `canceled` / `created`.** Эмиссия из
  `create/update_appointment`, маршрутизация врачам.
- **P4 — Сводки.** `day.morning` / `day.evening`, tz-aware скан, guard непустого
  дня. Плюс префы/тихие часы в полном объёме.
- **P5 — Деньги.** `debt.created` / `debt.settled` / `cash.dayClosed` →
  владелец/менеджер.
- **P6 — Подписка и команда.** `subscription.*` (переиспользовать существующие
  use-case'ы), `staff.*` / `role.changed`.

## 8. Риски

- **iOS тихие пуши** доставляются по усмотрению системы и режутся по частоте —
  `sync.day` не строить как единственный источник правды, только ускорение.
- **Протухание токенов** молчаливое — без чистки по `NotRegistered` таблица
  `device` копит мусор и растит стоимость рассылки.
- **Гонка «пуш ушёл — транзакция откатилась»** — эмиссия строго после commit.
- **Мультитаймзон** — единственный UTC-cron верен только пока все клиники в
  одном поясе; заложить скан заранее дешевле переделки.
- **Дубли на два устройства** — снимает `data.id` на клиенте, но сервер обязан
  давать его стабильным.

## 9. Тестирование

Существующая инфраструктура: testcontainers Postgres + миграции + fakeredis +
httpx (`tests/api/`).

- **Юнит** `PushDispatcher`: резолв получателей по ролям, применение `disabled`,
  тихие часы (digest откладывается, срочные идут), рендер текста по locale,
  стабильность `data.id`/`collapseKey`, `subscription.*` игнорирует `disabled`.
- **Транспорт**: фейковый FCM/APNs — проверка формы payload и удаления токена по
  `NotRegistered`.
- **API**: регистрация/снятие устройства, префы (идемпотентность PUT).
- **Cron-сканы**: `scan_due_appointments` не шлёт при тронутом статусе, на
  черновике (NULL-дата), повторно (по `push_event`); сводки не шлют пустой день.
