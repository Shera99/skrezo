✓ 02.09 · все 9 инкрементов

Одно событие → один инбокс → две доставки. Диспетчер — единственное место, где решается «кому и как». Строится на фундаменте P0, с переездом на outbox по таблице сверки выше.

  1. ✓ Outbox: таблица event + NOTIFY + диспетчерСделано (0043): INSERT в одной транзакции — приёмы (created/moved/canceled/status_changed, включая «черновик → запись» = created), касса (payment.created из кассы и «завершить и оплатить»). Диспетчер-цикл в воркере: LISTEN (прямое asyncpg-соединение) + поллинг 30 с, покоммитно, attempts/5 + last_error; незнакомый тип (будущие ai.*) не блокирует очередь.   2. ✓ Инбокс: inbox_item + APIСделано: снимок (account+clinic), врач — только «своё», уникальность (event_id, account_id) = идемпотентность (покрыто тестом повторной обработки).   3. ✓ Приоритеты по горизонтуСделано: внутренняя шкала из четырёх ступеней (low → digest → normal → critical) = строки таблицы §5; «+1» отмены/переноса двигает по ней (отмена за 2 ч — critical, за 30 ч — normal без подавления); идущий приём — только инбокс. critical уже уходит пушем немедленно (минус disabled из префов)
  4. ✓ Живые пуши: FCM + APNsСделано: FCM HTTP v1 (OAuth сервис-аккаунтом, кеш токена) и APNs token-based (JWT ES256, HTTP/2, sandbox/prod) — юнит-тесты на MockTransport, живые ключи включаются конфигом (PUSH_ENABLED=true + креды: JSON/.p8 строкой или путём к файлу). ✓ 08.09 · ядро, кэш префикса, общие клиенты, мониторинг раз в час, второй воркер, ретеншн; S3 отменён

Целевая нагрузка: 100–150 клиник, у каждой свой WhatsApp, 15–50 пишущих пациентов в день. Это 2 000–7 500 диалогов и 10–60 тысяч входящих в сутки; в среднем 0,5–1,5 сообщения в секунду, в пиках 5–10. Для Postgres и HTTP это ничтожно — всё упирается в другое: на каждое сообщение ассистент делает 1–3 вызова модели по несколько секунд каждый. Узкое место не «запросов много», а «каждый запрос долго ждёт внешний сервис».

Что измерено на локальном стенде (один воркер, настройки по умолчанию, SQL-эхо включено): приём вебхука — 330–480 запросов/с, p95 160–320 мс при 50 параллельных; воркер без ассистента — 300 сообщений за 15 с ≈ 20/с, одно задание 0,21 с в среднем; диспетчер событий переварил те же 300 за 15 с со средней задержкой 0,2 с. Запас на тракте без модели — 2–4× от пикового спроса. Переписывать архитектуру не нужно — ни очередей Kafka, ни микросервисов: все находки ниже локальные и закрываются за считанные дни.
Закрыто 04.09 (effe996) — четыре пункта ниже были не «на вырост», а ошибками, которые проявились бы уже на десятке клиник: потерянные ответы при пакетных вебхуках (2), двойные ответы на быстрые сообщения (3), лавина эскалаций при троттлинге модели (4) и резюме, которые никогда не построятся (7).
